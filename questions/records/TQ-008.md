EXAMPLE RECORD (invented "Acme Orders" domain).

## Question

What is the casing convention for ValidationProblem error keys across endpoints? The GET list returns camelCase keys (customerName); POST /api/orders returns the C# member names (CustomerName), and its test matches case-insensitively, which hides the difference. Confirmed by reading the code: the POST `Validate` uses `ValidationResult.MemberNames` verbatim as dictionary keys, and `Results.ValidationProblem` does not rename them; the POST test (`Create_MoreThanTwoDecimalPlaces...`) uses `StringComparison.OrdinalIgnoreCase`. Not confirmed: the actual response body, because it was not run.

## Options

1. camelCase wire names everywhere, fixed on the POST side by camelCasing the member names, plus a case-sensitive POST test (recommended: one convention, matches JSON property naming).
2. Keep C# member names everywhere and change the GET side.
3. Leave as is and document the difference.

## Answer

Decided in OD-019: option 1, camelCase error keys everywhere and a case-sensitive POST test. The owner (product owner, tech lead and privacy roles) answered on 2026-11-20.
