## Decision

Answers TQ-013 with its option 3 plus a requirement. The per-user rate limit partitions on the principal's `NameIdentifier` claim, then `sub`, as built (`OrdersRateLimit.PartitionKey`). Binding on later work:

1. The identity provider must issue `NameIdentifier` or `sub` as a stable, per-caller id for every token that calls the orders API, including non-user tokens (client credentials, service accounts) if any call it. Never a name or customer data.
2. A token with neither claim shares one bucket (`anonymous`). The partition count stays bounded, but such callers throttle each other; this is documented, not a defect.
3. Each adopter confirms what its identity provider issues (and whether the JWT bearer handler maps `sub`) when the provider is chosen, and records a TQ if it differs from this decision. Until then the behaviour is as built and pinned by the `PartitionKey_*` unit tests.
4. A configured claim type, or partitioning service tokens by client id, is not added now; it would need a new decision.

The requirement is stated in `src/Api/CLAUDE.md` (Limits row).
