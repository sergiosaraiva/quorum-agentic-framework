EXAMPLE RECORD (invented "Acme Orders" domain).

## Question

OD-018 decided that a trigram GIN index (a reviewed migration, Immutable Rule 2) and a minimum search-term length of 3 are added when the order table exceeds about 500,000 rows or the search p95 exceeds 300 ms. The local measurement of OD-030 (1,000,000 orders, one shared machine, seeded data) shows the trigger: a `customerName` search on the deepest page or with a broad term had a p95 of 0.31 to 0.58 s in all runs (the selective term on page 1: 0.29 to 0.46 s), because it costs two sequential scans; the page cap (OD-030) does not change it. Trigger: about 500,000 rows or p95 above 300 ms. Non-blocking: the index is not added in the TQ-016 change. When is it built, and with which term-length rule?

## Options

1. Add the `pg_trgm` extension and a GIN index on `customer_name` through a reviewed migration (concurrent index build, `suppressTransaction`), plus a minimum `customerName` term length of 3 (a 400 below it, an Option), with a migration test and a re-measure with `LoadMeasurementTests`, before the production order table passes about 500,000 rows (recommended).
2. Accept the limit: no index, rely on the rate limit, the concurrency limit and the command timeout; the search stays two sequential scans and its cost grows linearly with rows.
3. Another access path (for example keyset paging or a search service) if the term-length rule breaks a recorded user need.

- 2026-11-20: raised by the code-engineer from the review of the TQ-016 change (finding F2): OD-018 trigger reached at lab size, index deliberately not added in that change. Non-blocking.
