EXAMPLE RECORD (invented "Acme Orders" domain).

## Decision

Answers the security review question (SEC-001, Medium) raised against OD-025 and OD-018: the fixed-window rate limit bounds requests per window but not how many slow list requests one user holds open at once. Two additions, both Options with `[Range]`, `ValidateOnStart` and defaults in `appsettings.json`:

1. `RateLimiting:ConcurrentRequestsPerUser` (range 1 to 1000, default 4): the built-in concurrency limiter, partitioned like the rate limiter (`NameIdentifier`, then `sub`, OD-026), no queue. A request over the limit is a 429 `application/problem+json` of the same shape as the fixed-window 429 (fixed title, type, `traceId`; no `Retry-After`, because there is no window to wait for). It applies only to endpoints that carry the orders list policy. The built-in limiter allows one limiter per policy, so it is registered as the global limiter and matches on the policy name.
2. `Database:RetryAfterSeconds` (range 1 to 3600, default 5): the value of the `Retry-After` header on the 503 answered for a command timeout (OD-025).

The defaults 4 and 5 are chosen under the owner's delegation, not measured limits; revisit them at the pre-release load test (TQ-016). Not an accepted risk.
