EXAMPLE RECORD (invented "Acme Orders" domain).

## Question

OD-004 replaces the code statuses open, paid, cancelled with the BC-001 states. BC-001 does not say how legacy rows map, nor which state a new order starts in. What mapping does the migration use, and is a two-step rollout needed (the Infrastructure guide treats a narrowing change as destructive)?

## Options

1. `open` -> `draft`, `paid` -> `paid`, `cancelled` -> migration aborts (BQ-009); new orders start as `draft`; Down maps placed -> open, shipped and closed -> paid (recommended: conservative, see below).
2. `open` -> `placed`: asserts that lines and prices were frozen, which no code enforced; rejected.
3. `cancelled` -> `closed`: asserts delivery or refund and a settled invoice (BC-001 definition of closed); rejected.
4. Add a transitional constraint that accepts old and new values, then tighten in a second migration (a two-step rollout; only worthwhile if old and new API versions run against one database at the same time).

## Working assumption (non-blocking)

Option 1. Reasons: `paid` is the only exact match. `open` rows carry only a customer name and a total and nothing marks them as placed, so `draft` (BC-001: editable freely) claims the least. A new order starts as `draft` because BC-001 describes the customer editing a draft and says placing freezes lines and prices; BC-001 does not name the initial state explicitly. The migration is a single step: it runs as a deploy-time job (Infrastructure guide) before the new API serves traffic. If old API instances can run against the migrated database, the owner chooses option 4. Down cannot be exact (five states back to three); it is documented in the migration. Assumptions: the `order` table is small enough that the UPDATE and the constraint re-validation (which lock the table) are acceptable inside the deploy window; the row count has not been measured, and a large table would need a batched update and `NOT VALID` plus `VALIDATE CONSTRAINT`. The migration needs review before any shared environment (Immutable Rule 2).
