EXAMPLE RECORD (invented "Acme Orders" domain).

## Question

OD-018 added a 30 s default command timeout and a per-user rate limit. Open points: (1) `page=2000000000` is accepted and forces a very large OFFSET; should the offset be capped, and at what value? (2) OD-018 intends to bound slow searches, but 30 s is long for a read; should reads get a lower timeout than the default? (3) The timeout currently applies to every EF command, migrations at deployment included (apply them with a separate timeout). (4) A command timeout surfaces as a 500 problem response; should it map to 503 or 504? Not measured: no load figures exist for the new limits.

## Options

1. Cap the offset from a validated option, set a lower read timeout, keep the default for writes, map a timeout to 504 (recommended once a load figure exists).
2. Keep the single timeout and the 500 until a measured need.
3. Cap the offset only.

## Answer

Decided in OD-025: option 1, adjusted. The page number is capped by the validated option `Orders:MaxPageNumber` (default 10000; a page above it is a 400 keyed `page`); the single command timeout default is lowered from 30 to 10 seconds (no separate read timeout); migrations set their own timeout for their run; a command timeout is a 503 problem response with fixed text, not a 504. Answered on 2026-11-20 on the owner's delegation to the session's recommendation.
