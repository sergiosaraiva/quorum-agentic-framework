## Decision

Answers TQ-015 with its option 1, adjusted: three bounds on the cost of `GET /api/orders`, all Options, none a literal in logic.

1. Page cap. `Orders:MaxPageNumber` (`OrdersOptions.MaxPageNumber`, `[Range(1, 1000000)]`, `ValidateOnStart`, default 10000) is the highest page a caller may request, so the row offset is at most `(MaxPageNumber - 1) * MaxPageSize`. A page above the cap is a 400 `application/problem+json` keyed `page` with the fixed message `page must be at most <cap>.` (the configured cap, never the caller's value). Other values keep their behaviour: zero and negative pages clamp to 1, `pageSize` clamps to `MaxPageSize`, malformed text stays a 400 (OD-016).
2. Command timeout. The default of `Database:CommandTimeoutSeconds` is lowered from 30 to 10 (still `[Range(1, 600)]`, `ValidateOnStart`). The basis is the worst measured search of 0.4 to 1.6 seconds at 1M rows (TQ-007). There is one timeout for every EF command, reads and writes alike; a separate read timeout is not added. A process that applies migrations through this host's configuration (for example `dotnet ef`) must set its own larger `Database:CommandTimeoutSeconds` for that run; the migration job is not bound by the API default (the test factories set their own migration timeout on the context).
3. Timeout response. A command or connection timeout (a `TimeoutException` within 8 levels of the exception chain, which is how Npgsql reports a client-side timeout, or SQLSTATE 57014 from the server; an exception whose outermost type is an `OperationCanceledException` is a caller cancel and is not a timeout) is answered with 503 `application/problem+json` with a fixed title and detail and no exception text, through the exception handler's `StatusCodeSelector` and the problem details pipeline. 503 and not 504, because the API is the origin server, not a gateway waiting on an upstream. Every other exception keeps its status (a 500, or the 4xx of a `BadHttpRequestException`). The `Retry-After` header is added by OD-029.

The numbers 10 (timeout seconds), 10000 (maximum page number) and 1,000,000 (upper range bound) are chosen defaults under the owner's delegation, not measured limits. No load figure exists for them; the owner or tech lead revisits them at the pre-release load test (`tests/CLAUDE.md`, Gates). Not an accepted risk (no `accepted_risk`). Code and tests are in the branch that records this decision.
