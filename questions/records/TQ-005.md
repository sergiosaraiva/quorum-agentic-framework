EXAMPLE RECORD (invented "Acme Orders" domain).

## Question

`src/Api/CLAUDE.md` (Errors) requires RFC 9457 problem details for errors. A minimal API parameter typed `int?` or `DateOnly?` that fails to bind does not produce one. A probe on .NET 10.0.401 with `AddProblemDetails()` and `UseExceptionHandler()` (the same setup as `src/Api/Program.cs`) gave these results. In Production, `?page=abc` or `?from=2026-13-40` returns 400 with an empty body. In Development, the framework throws `BadHttpRequestException`, and the exception handler turns it into a 500 problem+json. Default `DateOnly` binding also accepts culture formats such as `11/19/2026` and silently drops a time part (`2026-11-19T10:00:00`). The landed VS-001 list endpoint (`OrdersEndpoints` `MapGet("/"`) has this gap for `page` and `pageSize`. VS-004 R1 avoids it for its new parameters by binding them as `string?` and parsing them explicitly. Which project-wide rule should list endpoints follow?

## Options

1. Bind query parameters that can be malformed as `string?` and parse them explicitly, returning `Results.ValidationProblem` (recommended for now: no global behaviour change, an error keyed by parameter name, the shape the POST endpoint already uses). VS-004 R1 does this for its new parameters only.
2. Keep typed binding. Add `UseStatusCodePages()` so a bare 400 gets a problem details body, and map `BadHttpRequestException` to its own status in the exception handler (`ExceptionHandlerOptions.StatusCodeSelector`), so Development does not return 500. This changes every endpoint and needs its own test, but the error does not name the field.
3. Leave it as is (rejected: it contradicts the Errors convention, and Development reports a client error as a server error).
