EXAMPLE RECORD (invented "Acme Orders" domain).

## Decision

Answers TQ-016 with its option 1, using its own rule (lower `Orders:MaxPageNumber` first; keyset paging only if a lower cap breaks a recorded user need). Every figure below is one data point from one machine (see Limits): not a production figure, and it must be re-measured on the deployment target before the first release.

1. Pool size. New option `Database:MaxPoolSize` (`DatabaseOptions.MaxPoolSize`, `[Range(1, 1000)]`, `ValidateOnStart`, default 20, in `appsettings.json`). `DatabaseConnectionString.WithPoolSettings` applies it through `NpgsqlConnectionStringBuilder` to `ConnectionStrings:Default` (which stays in configuration, never in the repo). The options win over the same keys written in the string, pooling is always on (`Pooling=false` in the string cannot disable the bound), and a `Minimum Pool Size` above the maximum is capped at the maximum. The default 20 rests on two things, not on a latency ranking: (a) the arithmetic against the server limit: instances times `MaxPoolSize` must stay below `max_connections` (default 100) minus the connections other clients need, and 20 allows 4 instances; (b) the failure evidence: with the Npgsql default of 100, 25 or more users sending the worst deep request reached 99 client connections and PostgreSQL error 53300 "too many clients", answered as 500 (5 responses at 25 users and 426 at 50 users in the final run), and the same server limit starves every other client (health checks, migration job, other instances). Sizes 50, 20 and 10 produced no 53300 in any run. 20 also lets 5 users send their allowed 4 concurrent requests each without waiting for a connection (peak 20 client connections at 5 users). The p50 and p95 differences between pool sizes in the tables are within the noise of a shared machine (single runs) and are not evidence for a size; throughput under overload was limited by the database CPU, not by the pool. The rule for an adopter: set it from `max_connections`, the number of instances and the other clients.
2. Connection wait. New option `Database:ConnectionWaitTimeoutSeconds` (Npgsql `Timeout`, `[Range(1, 300)]`, `ValidateOnStart`, default 5, applied by the same builder; the Npgsql default is 15). It is how long a request waits for a free pooled connection before failing as the 503 with `Retry-After` of OD-025 and OD-029, so a saturated pool sheds load after 5 s instead of holding the request for 15 s or more. A list request runs two commands (count, then the page), each taking a connection from the pool, so the worst case for one request is about 2 x (wait + command timeout) = 30 s at the defaults (observed maximum of a 200 response in the final run: 15.5 s). 5 is a chosen default, not a measured optimum. In an earlier run with the 15 s wait and a similar workload the p95 at 50 users and pool 20 was 26.6 s with no 503; with the 5 s wait the same cell answered 599 of 1000 requests with 503 and the p95 of the successful ones was 12.1 s: the wait decides how overload shows (late success or early 503), it does not add capacity.
3. Page cap. `Orders:MaxPageNumber` default lowered from 10000 to 1000 (`[Range(1, 1_000_000)]` unchanged). New maximum row offset: `(1000 - 1) * 100 = 99,900` rows at the default page size cap (was 999,900). The page-10000 request had a p95 between 0.8 s and 2.2 s over eight measurements (three as the deepest-page scenario at the old cap, five depth sweeps), against the 300 ms budget (OD-018). Page 1000 is the largest swept page under 300 ms in all five depth sweeps (p95 121, 231, 241, 298 and 247 ms); page 1500 was over in four of five. On the busiest sweep it passed by 2 ms, so the deployment re-measure may need page 500. No record states a user need for pages beyond 1000 (a keyword search of the records and the business KB for deep paging finds only TQ-016), so keyset paging stays deferred and a caller who needs the tail narrows with the filters (`createdFrom`, `createdTo`, `status`, `customerName`).
4. Trigram index. The OD-018 threshold ("about 500,000 rows or p95 above 300 ms") is reached at the lab size of 1,000,000 rows: a `customerName` search on the deepest page or with a broad term had a p95 of 0.31 to 0.58 s in all six runs, and the selective term on page 1 was over 300 ms in five of six runs (low end 0.29 s), because the search costs two sequential scans; the page cap does not help it. It is NOT added in this change (a reviewed migration with the `pg_trgm` extension and a minimum term length of 3 needs its own change and test). It is raised as TQ-017 (open, non-blocking, tech lead): add it before the production order table passes about 500,000 rows.
5. Unchanged, and the data do not contradict them: command timeout 10 s (OD-025), `RateLimiting:ConcurrentRequestsPerUser` 4 and `Database:RetryAfterSeconds` 5 (OD-029). One user's 4 simultaneous worst-case requests took p50 0.6 to 0.8 s and p95 0.8 to 1.1 s in the final run, at every pool size. Under the deliberate overload of 25 to 50 users at once the response time went to p50 8 to 12 s and p95 11 to 15 s because the database is saturated; the per-user limits bound one user, and the number of users that can overload one instance is an operations and capacity question for the deployment target (a global limit or load shedding is not added here).
6. Readiness shares the pool. `/health/ready` runs its database check through the same `DbContext` and so takes a connection from the same pool. Under saturation (all connections busy for the connection wait) the probe can wait or time out and report not ready, so an orchestrator can restart or unroute an instance that is only busy. The deployment sets the probe timeout and failure threshold with that in mind (a deployment follow-up for the chosen target); a separate pool for probes is not added here.

## Measurement

Tool: `tests/Api.IntegrationTests/LoadMeasurementTests.cs` (explicit, not run by `dotnet test`; command and duration in `tests/CLAUDE.md`). Seeded with `generate_series` in one seeded session, integrity on, `ANALYZE` run; the real API in process through `WebApplicationFactory` with an authenticated test user and only the per-user fixed-window limit raised (the concurrency limit, command timeout, pool and wait settings are the real ones). The tables below are the last of six runs, made with the final defaults (`MaxPageNumber` 1000, `MaxPageSize` 100, `MaxPoolSize` 20, `ConnectionWaitTimeoutSeconds` 5), 30 repetitions per scenario after 3 discarded warm-ups, 5 rounds per concurrency cell, 14 min 58 s.

Machine and data (2026-11-20): 22 logical CPUs, 31 GiB memory, Docker Engine on a WSL2 Linux guest, `postgres:16-alpine` (PostgreSQL 16.16, default server settings, `max_connections` 100), .NET 10.0.12, API and database on the same machine. The machine was shared with other workloads: the load average sampled at the start of the runs was between 3.6 and 39 on 22 CPUs, so every figure is noisy and, if anything, pessimistic. Table: 1,000,000 orders (159 MB with indexes), 49,988 distinct customers with a heavy-tailed spread, `created_at` over 3 years skewed to recent dates (2023-11-21 to 2026-11-19), status mix closed 40%, shipped 20%, placed 15%, paid 15%, draft 10%, random UUID ids.

## Limits

- Single machine, no network between API and database (in-process host, same CPUs as the database), one table shape (the order list only), seeded synthetic data with a chosen skew, default PostgreSQL settings, a warm cache, one image.
- The machine was shared with other work; run-to-run variation was up to 2.4 times for the same page (page 2000: p95 189 ms and 458 ms in two runs). Treat the numbers as an order of magnitude and a ranking, not as capacities, and do not read a pool-size preference out of the latency columns.
- Not measured: network latency, a managed database service, connection poolers, several API instances, cold cache, writes during reads, JWT validation against a real identity provider, readiness probes under load, the list under real customer-name distributions.
- The numbers must be re-measured on the real deployment target before the first release, with the same tool (a deployment follow-up; no new TQ because the target is not chosen, as for OD-027). Pool size, wait and cap are Options, so the re-measure needs no code change unless the answer is the index (TQ-017) or keyset paging.
