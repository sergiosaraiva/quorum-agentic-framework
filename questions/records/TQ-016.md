EXAMPLE RECORD (invented "Acme Orders" domain).

## Question

The page cap (OD-025), the 10 s command timeout and the per-user limits (OD-018, OD-029) are chosen defaults, not measured. Two points are open. (1) The Npgsql connection pool size is the library default; should the connection string set an explicit `Maximum Pool Size` so that concurrent list requests across all users cannot exhaust the database's connection limit? (2) Before the first release, a load test should request `page=MaxPageNumber` with `pageSize=MaxPageSize` and a selective `customerName` at the largest planned table size. If the worst case is over the latency budget, which change applies: a lower `MaxPageNumber`, or keyset paging?

## Options

1. Set an explicit `Maximum Pool Size` from the deployment configuration and run the load test (k6, `tests/CLAUDE.md`, Gates) before release; if over budget, lower `MaxPageNumber` first, and move to keyset paging only if a lower cap breaks a recorded user need (recommended).
2. Go straight to keyset paging now (a contract change for `page`).
3. Keep the library default pool size and the chosen caps until a production signal.

## Answer

Decided in OD-030: option 1. `Database:MaxPoolSize` (default 20) is applied to the connection string from validated Options; a local measurement at 1,000,000 orders showed the deepest page over the 300 ms budget, so `Orders:MaxPageNumber` is lowered from 10000 to 1000 (maximum offset 99,900 rows) and keyset paging stays deferred; the trigram index threshold of OD-018 is reached at that size and is recorded as a follow-up, not added. The figures are one single-machine data point and are re-measured on the deployment target before release.
