EXAMPLE RECORD (invented "Acme Orders" domain).

## Decision

Answers TQ-016 with its option 1, using its own rule (lower `Orders:MaxPageNumber` first; keyset paging only if a lower cap breaks a recorded user need). Every figure below is one data point from one machine (see Limits): not a production figure, and it must be re-measured on the deployment target before the first release.

1. Pool size. New option `Database:MaxPoolSize` (`DatabaseOptions.MaxPoolSize`, `[Range(1, 1000)]`, `ValidateOnStart`, default 20, in `appsettings.json`). `DatabaseConnectionString.WithMaxPoolSize` applies it through `NpgsqlConnectionStringBuilder` to `ConnectionStrings:Default` (which stays in configuration, never in the repo); the option wins over a `Maximum Pool Size` written in the string. Why 20: the Npgsql default of 100 reached the server's `max_connections` (100) under 25 or more users sending the worst deep request (99 client connections, PostgreSQL error 53300 "too many clients", answered as 500) and would also starve every other client of that server (health checks, migration job, other instances). Sizes 50, 20 and 10 produced no 53300. Size 10 queued earlier (p95 19.4 s against 13.0 s at 25 users on the same workload, 503s at 50 users) and 20 is the first size that gives each of 5 users their allowed 4 concurrent requests without waiting for a connection (peak 20 client connections at 5 users). The rule for an adopter: instances times `MaxPoolSize` stays below the server `max_connections` minus the connections other clients need (20 allows 4 instances against the default of 100). Throughput under overload did not depend on the pool size (database CPU was the limit); the pool only decides where a request waits and whether the server limit is hit.
2. Page cap. `Orders:MaxPageNumber` default lowered from 10000 to 1000 (`[Range(1, 1_000_000)]` unchanged). New maximum row offset: `(1000 - 1) * 100 = 99,900` rows at the default page size cap (was 999,900). Why: the deepest page with no filter at the old cap had a p95 between 0.8 s and 2.2 s over five runs (a 300 ms budget, OD-018); the cheapest page that stayed under 300 ms in every depth sweep was page 1000 (p95 121, 231, 241 and 298 ms in four sweeps; page 1500 was over in three of four). Page 1000 is the largest swept page that passed in all four, so it is chosen; on the busiest run it passed by 2 ms, so the deployment re-measure may need page 500. No record states a user need for pages beyond 1000 (a keyword search of the records and the business KB for deep paging finds only TQ-016), so keyset paging stays deferred and a caller who needs the tail narrows with the filters (`createdFrom`, `createdTo`, `status`, `customerName`).
3. Trigram index. The OD-018 threshold ("about 500,000 rows or p95 above 300 ms") is reached at the lab size of 1,000,000 rows: a `customerName` search on the deepest page or with a broad term had a p95 of 0.31 to 0.58 s in all five runs (the selective term on page 1: 0.29 to 0.46 s), over the budget whatever the page, because it costs two sequential scans. It is NOT added in this change (a reviewed migration with the `pg_trgm` extension and a minimum term length of 3, as OD-018 states, needs its own change and test). Follow-up for the tech lead: add it before the production order table passes about 500,000 rows; this record is the evidence that the lab table of 1M rows needs it to hold 300 ms. The page cap does not help this query.
4. Unchanged, and the data do not contradict them: command timeout 10 s (OD-025), `RateLimiting:ConcurrentRequestsPerUser` 4 and `Database:RetryAfterSeconds` 5 (OD-029). One user's 4 simultaneous worst-case requests took p50 0.5 to 0.7 s and p95 0.6 to 1.3 s on the final defaults. Under the deliberate overload of 25 to 50 users at once the response time went to p50 8 to 23 s and p95 11 to 30 s, because the database is saturated; the limits per user are what bound a single user, and the number of users that can overload one instance is an operations and capacity question for the deployment target (a global limit or load shedding is not added here).

## Measurement

Tool: `tests/Api.IntegrationTests/LoadMeasurementTests.cs` (explicit, not run by `dotnet test`; command and duration in `tests/CLAUDE.md`). Seeded with `generate_series` in one seeded session, integrity on, `ANALYZE` run; the real API in process through `WebApplicationFactory` with an authenticated test user and only the per-user fixed-window limit raised (the concurrency limit, command timeout and pool settings are the real ones).

Machine and data (2026-11-20): 22 logical CPUs, 31 GiB memory, Docker Engine on a WSL2 Linux guest, `postgres:16-alpine` (PostgreSQL 16.16, default server settings, `max_connections` 100), .NET 10.0.12, API and database on the same machine. The machine was shared with other workloads: the load average sampled around the runs was between 8 and 39 on 22 CPUs, so every figure is noisy and, if anything, pessimistic. Table: 1,000,000 orders (158 MB with indexes), 49,988 distinct customers with a heavy-tailed spread, `created_at` over 3 years skewed to recent dates (2023-11-21 to 2026-11-19), status mix closed 40%, shipped 20%, placed 15%, paid 15%, draft 10%, random UUID ids. Repetitions: 30 per scenario after 3 discarded warm-ups; 5 rounds per concurrency cell.

## Limits

- Single machine, no network between API and database (in-process host, same CPUs as the database), one table shape (the order list only), seeded synthetic data with a chosen skew, default PostgreSQL settings, a warm cache, one image.
- The machine was shared with other work; run-to-run variation was up to 2.4 times for the same page (page 2000: p95 189 ms and 458 ms in two runs). Treat the numbers as an order of magnitude and a ranking, not as capacities.
- Not measured: network latency, a managed database service, connection poolers, several API instances, cold cache, writes during reads, JWT validation against a real identity provider, the list under real customer-name distributions.
- The numbers must be re-measured on the real deployment target before the first release, with the same tool (a deployment follow-up; no new TQ because the target is not chosen, as for OD-027). Pool size and cap are Options, so the re-measure needs no code change unless the answer is a new index or keyset paging.
