EXAMPLE RECORD (invented "Acme Orders" domain).

## Question

`OD-003` makes the customer-name search case-insensitive. VS-004 R1 implements it with PostgreSQL `ILIKE` (`EF.Functions.ILike`). PostgreSQL applies the database's character type (`LC_CTYPE`) when it compares case. A probe on `postgres:16-alpine` returned these results. In the default `en_US.utf8` database, `'ÉCOLE' ILIKE '%école%'` is true. In a database created with `LOCALE 'C'`, it is false; ASCII letters match in both. The deployment target and its database creation parameters are not recorded (`{{DEPLOY_TARGET}}`). Should the project fix the database locale, or make case-insensitivity independent of it?

## Options

1. Require every environment's database to be created with a UTF-8 `LC_CTYPE` (for example `en_US.utf8`), written into the infrastructure code, and keep `ILIKE` (recommended: no migration, matches the test container).
2. Use an ICU collation or the `citext` type on `customer_name` (a migration). Note that PostgreSQL 16 does not support `LIKE`/`ILIKE` on nondeterministic collations.
3. Accept ASCII-only case-insensitivity and record it as a limitation.

## History

- 2026-11-19: raised by solution-architect during the VS-004 R1 design, with the probe result above. Does not block VS-004 R1, whose tests cover ASCII names and one accented name in the test container's `en_US.utf8` database.
